# Phase 4c: Gradio UI Implementation Plan

**Owner:** Neha
**Status:** Draft
**Date:** 2026-11-15
**Issue:** #10

## Goal

Complete the Gradio chat UI as a thin adapter over the existing
CodeForge LangGraph pipeline. All business logic remains in the graph
and existing Python modules.

## Current implementation

- Gradio Blocks interface and Chatbot.
- Existing LangGraph integration.
- Explicit approval and rejection using Command(resume=...).
- Approval screen displays policy verdict, reasons, generated code
  and tests.
- Final response displays the graph's existing report.

## Tasks

### 1. Protect Request privacy
- Display only the masked Request returned by the graph.
- Never echo the original unmasked message.
- Do not expose raw exception details in the UI.

### 2. Approval screen
- Include the Serving tier in the approval details.
- Preserve the existing explicit Approve and Reject actions.
- Only an explicit approval may resume execution.

### 3. Final report
- Display the graph-generated report without reconstructing results.
- Preserve the actual pytest exit code, summary and timeout outcome.
- Display the Serving tier when available.

### 4. Error handling
- Show clear, specific and honest errors.
- Do not expose secrets, personal data or internal exception details.

### 5. Feedback integration
- Add a thumbs-down action linked to the real Feedback store.
- Dependency: Feedback model, table and creation method must exist.
- Do not implement a fake UI-only feedback action.

### 6. Verification
- Launch the Gradio application.
- Manually test the approval path.
- Manually test the rejection path and confirm nothing executes.
- Verify masked Request display.
- Verify actual pytest result and Serving tier.
- Run relevant unit tests and the full test suite.
- Record actual commands, exit codes and results.

## Constraints

- Gradio remains a thin adapter over the same graph.
- No duplicated business logic in ui/.
- No automatic approval.
- Never expose unmasked input.
- Do not weaken security or golden-case invariants.
- Do not add dependencies or modify CI without team agreement.
- Preserve existing user changes.

## Dependencies and unresolved items

- R1 masking and R2 sandbox hardening are owned by the policy team.
- Feedback integration depends on the shared Feedback store.
- R6 gate readiness must be confirmed before treating the phase as
  complete.
- Serving tier must come from graph state, not a UI assumption.

## Completion criteria

- Approval and rejection paths manually verified.
- UI displays masked input and honest execution results.
- Feedback integration works when the shared store is available.
- Tests pass with actual exit codes recorded.
- Tracker updated with evidence.
